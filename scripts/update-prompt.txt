You're maintaining a public BI dashboard of Google + Booking.com reviews for the "Queen of Sheba" hotel in Eilat, running locally on the owner's own PC (this repo is already cloned at the current working directory, and `git push` works without prompting because a GitHub credential is already cached here via `gh auth login` — you don't need to set up auth). ## Your task, each run

1. Read HANDOFF.md fully before doing anything else — it documents *why* each scraper is built the way it is (Google's trusted-input-event requirements and ~30-review pagination plateau; Booking's real page-numbered pagination and exact dates), which matters if something below fails and you need to adapt.
2. `git pull --quiet` first, so you're never working on stale files. If it fails, stop and go to the failure path.
3. Run both scrape+merge pairs (independent of each other — a failure in one should NOT block the other; run both, then decide what to commit):
   - **Google**: `node scripts/scrape-reviews.js scripts/.last-dump.txt` (opens the Google-hosted reviews page, sorts by newest, expands truncated text, scrolls to the ~30-review/~9-day plateau — EXPECTED, not a failure; see HANDOFF.md) then `node scripts/merge-and-build.js scripts/.last-dump.txt` (parses, dedupes by content hash, merges, updates today's snapshot row). Prints `scraped=N added=M totalInDataset=K`.
   - **Booking**: `node scripts/scrape-booking-reviews.js scripts/.last-booking-dump.json --days=45` (sorts newest-first, paginates with real page numbers until reviews older than 45 days — no hard cap like Google, so a shorter daily window is enough; the initial backfill already got ~100 days) then `node scripts/merge-booking.js scripts/.last-booking-dump.json` (converts to the unified schema — 10-point score rounded to 1-5★, positive/negative text combined, exact dates — dedupes by `reviewer+date+title` hash, merges, updates today's snapshot row with `booking_rating_10`/`booking_reviews_total`). Prints the same `scraped=/added=/totalInDataset=` summary.
   - **Enrichment (required — do not skip)**: `node scripts/enrich-llm.js`. This reads each newly-merged review with an LLM and adds its `llm` block (themes, per-theme sentiment, staff mentions, summary, severity, rating/text-mismatch flag). The dashboard's theme sentiment, urgent-board summaries and the entire staff tab are built from it, so a day skipped here means those views quietly go stale for the new reviews. It only enriches reviews that lack the block, so it is safe and cheap to run every day (typically ~10 reviews). If it reports failures, they are almost always transient connection errors — run it once more; it resumes where it left off. If it still fails, commit the merged data anyway (the dashboard falls back to keyword themes) and note it in STATUS.md.
4. Run `npm test` (51 checks: theme matching, parser regressions, stored-data integrity, and a headless render of every tab at desktop and mobile). If it fails, do NOT commit — go to the failure path and include the failing check names in STATUS.md.
5. Sanity-check before committing (apply to whichever of Google/Booking actually ran successfully):
   - `totalInDataset` must be `>=` what it was before this run (`git diff --stat data/reviews.json` should show only insertions; large deletions → STOP, don't commit, go to the failure path for that source).
   - Both JSON files must still be valid JSON (`node -e "JSON.parse(require('fs').readFileSync('data/reviews.json'))"`, same for snapshots.json) — parse failure → STOP, don't commit, go to the failure path.
   - `added=0` is a normal no-op (nothing new since yesterday), not a failure — still commit if today's snapshot row changed.
   - If BOTH sources added nothing AND today's snapshot is byte-identical to yesterday's, nothing to commit — clean no-op, end the session.
6. Commit & push (only reached if the checks above passed and there's an actual change — partial success is fine, e.g. Google worked but Booking didn't, commit what's good):
   - `git add data/reviews.json data/snapshots.json`
   - Commit message: `Auto-update: ביקורות ל-{YYYY-MM-DD} (Google: +{N}, Booking: +{M}, סה"כ {total})`
   - `git push`
   - Do NOT edit `reviews_dashboard.html` or any `scripts/*.js` as part of a normal successful run — those only change when you're actively fixing something broken, and any such fix should be its own separate, clearly-labeled commit plus a dated note in HANDOFF.md. If you DO change code, run `node scripts/stamp-build.js` before committing so the dashboard's visible "גרסת קוד" stamp matches what you shipped (a data-only run must NOT re-stamp — the code didn't change).

## Failure path (scrape errors, near-empty dump, unparseable output, or a sanity check in step 4 fails)

Do NOT modify `data/reviews.json` or `data/snapshots.json` for the source that failed if you're not confident the new data is correct — a partial/corrupt write is worse than a skipped day; the OTHER source can still proceed and commit normally. Create/update `STATUS.md` at repo root naming which source failed and exactly what was tried (stdout tail, error text, what the dump looked like). Commit and push that file (alongside any good data from the source that DID work): `Auto-update check failed for {Google|Booking}: see STATUS.md`. If a previous run left a `STATUS.md` and this run succeeds cleanly on all sources, delete it and commit that deletion alongside the normal update commit.

If a scraper is erroring in a way that looks like the site changed something structural (a selector that used to work now finds nothing, Google's sort-menu keyboard trick stops taking effect, Booking's `data-testid` attributes renamed, etc.), you're encouraged to actually debug and fix the relevant script in this same run rather than just giving up — you have full tool access. Use the last raw dump file to test parser changes quickly without re-scraping. If you fix something, document what broke and how in HANDOFF.md (dated entry).

## Ground rules
- Never fabricate or estimate review data. Every review in `data/reviews.json` must come from an actual scrape of its stated source.
- Never delete or overwrite existing reviews — each merge script's dedupe-by-hash logic is the only thing that should ever decide a review is "already there"; don't hand-edit the file.
- Keep `reviews_dashboard.html` a single self-contained file with no embedded data — it must keep working purely by fetching the two JSON files at runtime.
- This routine only ever touches reviews for THIS hotel (Google entity id `CgoIytfkyoX724ETEAE`, Booking slug `eilat-queen-of-sheba`) from Google and Booking.com specifically — never broaden scope to other hotels or other review sites (Tripadvisor's rating is tracked as a comparison figure only, scraped incidentally as part of the Google page, never as its own review source) without the owner explicitly asking.
